# App 需求规格（ミルコレ／見立て・パレイドリア App）

> 来源：用户的毕业设计项目（デジタルハリウッド大学大学院）。以 4 份会议记录（進捗1/2/3、中間発表）和 Project 内到 2026-10-01 为止的对话整理为准，其中 10 月 1 日的整理版是用户核对并更正过的最新内容。
> 标注说明：**【已定】** = 用户明确确定；**【未定】** = 尚未决定，不要擅自当作定论；**【假设】** = 为了能开工做的合理推断，需用户确认。

## 1. 基本信息与一句话定义

- **App 名称：ミルコレ**（見る × コレクション）【已定，9 月确定】。查过重名：东芝 REGZA 有一个读音相同的「みるコレ」（电视内容搜索服务），领域不同，判断中間発表阶段可以使用。（進捗3 会议时名字尚未定，那份记录里的"未定"已过时。）
- 形态：手机网页 App，三个主画面 + 侧边栏マイページ。7 月的版本里第三个画面曾叫「発見」，后来统一为「つながり」。

用户把日常里"看起来像什么"的瞬间拍下来 → 用手指描出闭合轮廓 → 补画细节并命名 → **収集页上显示的是"形"**：用描出的路径给照片做遮罩，只露出形的内部，背景被去掉；**点开"形"可以看到完整照片和当时描的轮廓**。【已定 2026-10-13】其他用户可以在同一张照片上描出不同的形，比较"见え方"的差异。【已定】

目的：缓解 SNS 造成的「情報疲れ」，把被动刷信息变成**主动观察**。灵感来自作者本人刷 SNS 疲惫时仰望天空、看云像动物或人脸而放松的体验。【已定】

## 2. 核心机制（最重要，必须在所有界面与说明中显式体现）

**「先に描く、それから見る」（先画，再看）**【已定】
- 「つながり」的大部分卡片是**纯看**（别人描的形，直接可见）。**只有个别几张**混在其中的是"先描再看"卡：还没人描过，或你自己还没描过的照片，只显示「あなたには何に見えますか？」。【已定 2026-10-13】
- 可以跳过，也可以自己描；**描完之后才解锁其他人对同一张照片的描法**。
- "先描再看"里的描，**只需要描一圈轮廓**，不需要描き足し和取名字（那两步只属于記録）。【已定 2026-10-13】
- 在别人的照片上描的形**不进自己的収集**。【已定 2026-10-13】
- 这是与 Instagram / Pinterest 等被动浏览型服务的核心差异点，不能当作"隐含"的，文案里必须明说。

## 3. 目标用户与定位【已定】

- 想从 SNS 信息疲劳里抽身、但不是要"戒掉"SNS 的人；用在碎片时间里，替代被动刷 SNS。
- 用户既是"发现者"又是"创作者"。
- 与 Instagram/Pinterest 的区别：它们收集"美的/喜欢的东西"；本 App 收集的是**自己主观的见え方**。
- 与既有的パレイドリア社区的区别：那些只是看别人发现的形；本 App 让用户自己动手。

## 4. 屏幕结构

### 4.1 記録（Record）—— 创作入口【已定】
1. **撮る**：拍下"看起来像某样东西"的瞬间
2. **なぞる**：用手指沿形状描一圈闭合轮廓
3. **描き足す・名付ける**：在轮廓内补画眼睛、翅膀、脚等细节，再起名字
- 保存描出的闭合路径、补画的细节和名字，同时保存照片（压缩后存 IndexedDB）。収集页只显示"形"（照片被路径遮罩），点开才显示完整照片和轮廓。【已定 2026-10-13】
- 有**期間限定のチャレンジ入口按钮**，参加后当场消失（防止重复参加）。

### 4.2 収集（Collect）—— 完全个人的空间【已定】
- 不混入他人内容；**チャレンジ作品不进这里**。
- **显示方式**：只有自己描出的形状浮在页面上，没有卡片框、没有矩形容器、没有照片背景。实现思路：用手绘路径给照片做遮罩（形的内部是照片纹理），物理碰撞用椭圆。
- **详情**：点开一个形 → 显示完整照片，上面叠加当时描的轮廓、细节和名字。【已定 2026-10-13】
- **投稿・共有**：详情里有「⋯」按钮，菜单里是「つながりに投稿」（可取消）和「外部に共有」（照片＋轮廓＋名字合成一张图，用系统分享；不支持时下载）。投稿后这张照片和形以"纯看"卡出现在つながり。【已定 2026-10-13】
- **コレクション**：选一些形状、加上主题，整理成合集发表。
  - 合集用**玻璃瓶**呈现，形状装在瓶里。
  - 用陀螺仪感应手机倾斜和摇晃，瓶内形状按物理规律移动（Matter.js，已做过独立 demo，见 7.6）。
  - 每发表一次合集，解锁新的瓶子样式；未解锁的瓶位显示为剪影。
  - 瓶子外观也可以用点数自定义（见 5.2）。
  - 具体解锁条件（发表几次解锁几种）与瓶子样式数量【未定】。现在的占位：5 种，最初 1 种，每发表 1 次解锁 1 种，1 瓶最多 12 个形（`src/config/bottles.ts`）。
  - **创建入口【已实现 2026-10-13】**：収集页下方的瓶子棚里有「つくる」→ 选形 → 写主题、选瓶子 →「発表する」→ 直接打开瓶子。点棚上的瓶子可再次打开。
  - 瓶内交互：陀螺仪倾斜（iOS 用「傾けて動かす」按钮授权）、手指拖动、「ふる」按钮摇一摇。

### 4.3 つながり（Connect）—— 他人的解释【已定】
- 一张一张滑动浏览他人的形状（不是传统的无限信息流）。
- **滑动方式：卡片叠在一起，划走最上面一张，露出下面一张**（不是横向平移翻页）。左右划都只是"下一张"，不代表喜欢／不喜欢。【已定 2026-10-13】
- 自己的照片**只有主动投稿后**才会出现在つながり里；不投稿就只在自己的収集。【已定 2026-10-13】
- **第一张必定是当期官方お題**，每次打开都保证显示。
- 「先に描く、それから見る」见第 2 节。
- **月間ピックアップ**自然地混在 feed 里（见 5.3）。
- 右上角有**裏世界**的特殊图标入口。

### 4.4 マイページ（侧边栏）【已定】
- 基本信息、设置。
- 「月度回顾」入口：系统地回看过去的月間ピックアップ。定位低调，只有主动去找的人才会看到。

## 5. 功能模块

### 5.1 チャレンジ机能（运营方定期发布お題）【已定】
- 运营方定期出**一张照片**作为お題，用户各自描出自己的解读。看点是"同一张画布，解释不同"（参考：爽ハッピースプーン、Inktober 等）。
- **两个入口**：記録的限定按钮（参加后消失）；つながり feed 的第一张。
- 挑战作品**不进个人収集**，归档到**裏世界**。
- **裏世界**：
  - 极光（aurora）色系，配色与主界面不同，营造"进入隐藏空间"的非日常感。
  - **裏世界里没有瓶子**（瓶只属于収集）。
  - 先选「回」（每期主题）：默认显示最新一期，可左右滑动，也可切换成网格。
  - 进入某一期后，浏览方式和普通 feed 相同，可看所有参加者的解读。
  - **排列顺序：自己的作品排第一，其余参加者随机排列**，避免引发比较。
  - **没参加过的期默认只能看、不能画**；用点数兑换权利后，可以限定次数补参加。
- 每次参加获得点数。

### 5.2 点数（Points）【已定】
- **目前只能通过参加チャレンジ获得**。
- 点数不是可兑现的现金类积分，用于让自己的表达/体验更丰富。可兑换的 5 种用途：
  1. なぞる线条的颜色、粗细、质感（水彩风、铅笔风等）
  2. 収集玻璃瓶的颜色、质感、光效
  3. App 整体主题色（黄昏、深夜、初雪等限定配色）
  4. 补参加错过的チャレンジ（限定次数）
  5. 命名时的字体和文字装饰自由度
- 各项所需点数、获得点数的数值【未定】。

### 5.3 月間ピックアップ（月度精选）【已定】
- 从用户日常自由投稿的照片中（**不含お題照片**），每月自动选出**被最多人重新描过的一张**。看的是"哪张照片能引出最多种解释"，不是谁画得好。
- **没有排行榜、没有专用横幅、不显示任何数字**，直接自然地插在 feed 里。
- 滑到这张时才出现特殊演出（彩虹描边／弹出动画）。
- 点开可以看到这张照片最初的解读，以及当月所有参加者的解读。
- 被重新描的次数**对投稿者本人也不显示，也不通知**。

## 6. 硬性设计约束（详见 `02-design-principles.md`）

- 不做排名、不显示点赞/互动数等指标。【已定】
- 不引入"比赛＋奖项"等竞争机制（教授提议被否决，因为会重新带回 App 想缓解的竞争压力）。【已定】
- 评价对象是**照片**，不是人。【已定】
- 裏世界里自己的作品排第一、其他人随机排列，目的就是避免比较。【已定】

## 7. 技术与交付形态

**最终形态【已定】**：UI 时尚的、在手机浏览器里打开网址就能使用的**网页 App**（移动端优先）。测试阶段直接在手机真机上做。

### 7.1 技术约定
- 纯静态前端，部署到 **GitHub Pages（HTTPS）**。【已定】
- **不再要求"单文件 HTML"**【变更】：可以拆成多个 HTML/CSS/JS 文件，或用 Vite 等构建工具，产物必须仍是可直接放 GitHub Pages 的静态文件。选型由 Claude Code 决定，依赖尽量少。注意 Pages 项目页是子路径（`/仓库名/`），资源路径用相对路径或配置 base；用了构建工具就用 GitHub Actions 构建并发布。
- Matter.js（收藏页瓶子物理）、Lucide 图标、localStorage 持久化。【已定】
- UI 文案：日语（与用户沟通用中文）。【假设】

### 7.2 手机端要求
- 移动端优先：viewport meta、safe-area（刘海／底部横条）、`100dvh`，不出现横向滚动。
- 描线用 Canvas + pointer events，Canvas 上要禁止触摸滚动（`touch-action: none`），避免描线时页面跟着滑。
- 相机：基础方案用 `<input type="file" accept="image/*" capture>` 调起系统相机；`getUserMedia` 应用内取景为可选增强。两者都需要 HTTPS。
- 倾斜手机让形在瓶子里滚动：读取陀螺仪，iOS 需要由用户点击触发的授权请求；不支持或被拒绝时必须回退到触摸拖动／点按，不能让功能失效。
- 可添加到主屏幕：提供 manifest 和图标。**测试期不要用 service worker 做离线缓存**（会让测试者一直看到旧版本）。

### 7.3 数据与存储
- localStorage 只在各自手机的浏览器里，**无法在用户之间共享**。つながり 里"他人的描法"、月間ピックアップ的全体统计、运营方的お題，测试阶段全部用预置示例数据／本地配置文件模拟。【已定约束】
- **存储必须带版本号，数据结构变更时写迁移**，避免测试者已有收藏在更新后丢失。
- 【建议】localStorage 容量有限（约 5MB 量级）。"形"只存路径数据，体积小；用户自己拍的照片**需要保存**（収集的遮罩和详情都要用），压缩缩小（如长边 1280px 的 JPEG）后存 IndexedDB，不要以 dataURL 塞进 localStorage。
- 测试数据收集【建议】：App 内加"导出我的使用记录"按钮（JSON，**不含照片**），记录打开日期、描线次数、是否参加挑战；另放问卷链接（如 Google 表单）。首次引导里要说明数据只存在本机。

### 7.4 视觉风格【已定 2026-10-13：メンフィス】
- 参照 `design/style-preview-3.html`（G 案）。用户的要求：清爽、清新、扁平，**不要滥用渐变**。被否决的：A 紙と鉛筆／B 空とガラス／C 夜の観察室（`style-preview.html`），D/E/F 扁平案（`style-preview-2.html`）。
- 白底 `#FFFDF6`；黑色 2px 轮廓线 `#1A1A1A`；不模糊的黑色错位硬阴影；纯色：黄 `#FFD23F`、粉 `#FF8FB1`、青绿 `#3DCCC7`、淡紫 `#B79CFF`、蓝 `#3A6FF7`。**不用渐变**。
- 字体：标题 Dela Gothic One，正文 M PLUS Rounded 1c。圆角 12–18px。
- 装饰：背景少量几何图形（波浪线、三角、点阵、半圆、圆环），不要堆满。
- 收集里的形：贴纸样式（黑边 + 彩色错位阴影）；未解锁瓶子为虚线轮廓。
- 动效：形是定格式的"一顿一顿"晃动，不是平滑漂浮；按钮按下时沉入阴影位置。
- 裏世界：底色翻成深紫 `#2A1E5C`，同样的几何图形用亮色；极光感用纯色色块表达，不用渐变。
- 主题必须用 CSS 变量／设计 token 实现：点数可以兑换"App 主题色"，裏世界要有极光配色，月間ピックアップ要有彩虹边框演出，这些都依赖可切换的主题。

### 7.5 后续扩展（不在当前范围）
- 毕设之后若要做成真正公开使用的 App，需要加后端存用户、照片和投稿（Firebase、Supabase 这类现成服务）。前端界面不必推倒重来，主要是把数据层从 localStorage 换成后端。**当前不要提前做后端。**

### 7.6 既有素材（不在本包文件内）
- **旧概念（図鑑アプリ）的 HTML 原型**：已做过，单文件 HTML，Lucide 图标、底部 Sheet、侧边栏抽屉。**该概念已废弃，不要沿用図鑑逻辑**；「図鑑帳」「図鑑上」都是废弃概念的旧词，新 App 里不要出现。只可参考交互结构（底部 Sheet、抽屉）。它出现在 Project 对话「毕设html」（6/30）里。
- **玻璃瓶物理效果的独立 demo**（Matter.js + 陀螺仪）：已做过，出现在 Project 对话「Review feedback」（7/18）里。
- 这些代码不在 Project 文件里。如果用户另外提供，放在 `reference/` 目录，只作参考。

## 8. 验证计划（原型完成后）【已定】

- 5–10 人，数日内重复使用，之后做定性问卷。
- 关注点：なぞる体验是否直观；使用 App 后对日常的"看法"是否有变化。
- **目的是发现问题与改进方向，不是证明效果**（不做统计显著性论证）。
