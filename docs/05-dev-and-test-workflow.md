# 开发与测试流程

目标：测试期间能在手机上真实使用并看到效果，同时可以随时让 Claude Code 修改。

## 1. 发布链路（一次性搭好）
- 项目放进 GitHub 仓库，开启 GitHub Pages。
- 推送到 `main` 分支后自动发布（有构建步骤就用 GitHub Actions）。一两分钟后，手机刷新同一个网址即可看到新版本。
- 创建仓库、开启 Pages、授权登录这类步骤可能需要用户本人操作；Claude Code 做不了时，给出清晰的操作步骤即可，不要假装已完成。
- 作者和测试者用**同一个网址**，不再单独分发文件。

## 2. 分支与提交
- 日常开发在 `dev` 分支。确认没问题后再合并到 `main`，**测试者访问的永远是 `main`**。
- 同一个仓库、同一个 Pages 站点发布两份：`main` → `https://<用户名>.github.io/mirucolle/`（测试者用）；`dev` → `.../mirucolle/dev/`（作者真机自测用）。任一分支推送都会触发 Actions，把两个分支分别构建，再合并成一个产物发布。
- 两份网址同源（同一个 github.io 域名），**localStorage 键名和 IndexedDB 库名必须带环境前缀**（如 `mirucolle:` / `mirucolle-dev:`），避免互相覆盖。
- 每完成一个功能就提交一次，提交信息写清楚改了什么，方便回退。
- 每次只做一件事，别一次改很多不相关的东西。
- 改完先在浏览器里实际跑一遍（手机尺寸），再提交。别只检查代码。
- 需求有变时，**先更新 `docs/` 里的规格，再改代码**。

## 3. 验证环境
- 电脑上用手机尺寸预览，快速看版面和流程。
- 这些必须在**手机真机 + 部署后的 HTTPS 网址**上验证：描线手感、调起相机、陀螺仪、「添加到主屏幕」后的显示。局域网 HTTP 预览测不出相机和陀螺仪。
- iPhone Safari 和安卓 Chrome 表现有差异，正式测试前两边各试一遍。

## 4. 测试阶段节奏
1. **自测**：作者自己在手机上用。
2. **小范围试用**：1–2 个朋友用一两天，只为发现明显的坏点和看不懂的地方，修完再放开。
3. **正式测试**：5–10 人，连续使用数天，之后做定性问卷。
4. 正式测试期间**冻结功能，只修 bug**，保证测试者前后用的是同一个东西。
5. 数据结构一旦要变，必须带迁移（见规格 7.3），否则测试者的收藏会丢。
6. 避免 service worker 缓存，否则测试者会一直看到旧版本。

## 5. 看到效果
- 数据在测试者手机本地，默认看不到。靠两样东西收集：
  - "导出我的使用记录"（JSON，不含照片），测试者发给作者；
  - 问卷链接，收集定性反馈。
- 测试目的是**发现问题和改进方向**，不是证明有效；统计与结论写法按规格第 8 节。
